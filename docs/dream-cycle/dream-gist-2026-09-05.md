# Performance SOTA Report — 2026-09-05

TL;DR: Tonight's performance deep-dive found that Ruflo's own CLI cold-start "benchmark" suite (`v3/@claude-flow/performance/benchmarks/startup/*.bench.ts`) never measured the real CLI at all — every reported number, including a "V2 vs V3 Speedup: 5.00x" line, came from `setTimeout()` delays with no code in between, guaranteed to produce that ratio on every run regardless of any real behavior. A real, spawn-based measurement function (`measureColdStart()`) already existed in the file but was never called — dead code sitting next to its own fabricated replacement. Fixed: wired the real function into the suite, removed the fabricated V2-vs-V3 comparison outright (there is no V2 binary left to compare against), and added a deterministic Vitest regression test. Real measured number: CLI cold start via `node bin/cli.js --version` (the one subcommand that runs without a full `dist/` build in this worktree) averages **~54.7ms** over 5 runs — well under the 500ms target — but this covers only that subcommand, not full command initialization, so the broader "Achieved" claim in `ADR-STATUS-SUMMARY.md` is corrected to reflect what's actually verified. Also corrected the same table's already-known-false "150x-12,500x HNSW" claim to point at the real measured 1.9x-4.7x numbers. Security and hive-mind scans each surfaced one new, code-verified, low-cost-to-fix finding, documented below as candidates for future nights (not implemented tonight, to keep this patch to one conceptual change per repo convention).

## Scan Findings: security

Plugin supply-chain controls are documented but not enforced at install time (Medium severity, new, code-verified — not previously flagged). `v3/@claude-flow/cli/src/plugins/store/discovery.ts:96-102` defines real `PluginStoreConfig` fields (`requireVerification`, `minTrustLevel: 'community'`, `blockedPlugins`, `allowedPermissions`, `requirePermissionPrompt: true`) and `SECURITY.md` documents checksum verification, trust-level gating, and permission allowlisting as the threat model — but `commands/plugins.ts:217,228`'s `--verify` flag (default true) is read into a local variable and never referenced again (2 total grep hits: declaration + option definition); the registry entry's `checksum`/`trustLevel`/`permissions` are fetched only for cosmetic display (lines 271-309) while the actual install (`manager.installFromNpm`) runs a plain `npm install <name>` fully decoupled from that metadata; and a repo-wide grep for `config.blockedPlugins|minTrustLevel|allowedPermissions|requirePermissionPrompt` returns zero matches — these config gates are never read anywhere. `manager.ts`'s `enable()` just logs a sandboxing warning and flips the plugin on regardless of trust level or requested permissions. Net effect: an `unverified`-trust, `privileged`-permission-requesting registry entry installs and enables identically to an `official` one — no checksum check, no prompt, no block — despite the CLI's own display implying verification occurred. Distinct from `discovery.ts:186`'s registry-JSON-level signature check, which is real and fail-closed. Testable at low cost with a stubbed-npm unit test (proves `--verify=false` vs. default produce identical `installFromNpm` behavior, and an `unverified`/`privileged` mock entry installs unprompted). Not implemented tonight — candidate for a future `security` DEEP night or an immediate small follow-up PR.

## Scan Findings: hive-mind

Raft leader-election safety gap in `v3/@claude-flow/swarm/src/consensus/raft.ts` (new, code-verified, distinct from the previously-fixed `weightedConsensus()` and `TopologyManager.rebalanceHybrid()` bugs). `startElection()` (lines 303-333) iterates peers, calling `requestVote()` (335-368) and counting `votesReceived`. If a peer's response reveals a higher term, the node correctly steps down to follower internally (347-352) — but the outer loop keeps counting votes from *earlier* peers who granted under the node's original (now-stale) term. If a later peer in the same loop grants a vote after the internal term-bump, `votesReceived` can cross `votesNeeded` and `becomeLeader()` fires (line 370) unconditionally — no guard that all counted votes share the current term, and no check that the node is still in `candidate` state. Net effect: a node can be declared leader for a term via a "majority" that mixes votes cast for a stale term with votes for the current one, violating Raft's core safety property and potentially producing two simultaneous leaders for the same term. Existing test coverage (`raft-transport.test.ts`) only exercises the receiver side (`handleInboundRaftMessage` per-message); nothing drives `startElection()`/`becomeLeader()` through a multi-peer loop with a mid-loop term bump — grep confirms `startElection`/`becomeLeader` are invoked only from within `raft.ts` itself. Testable cheaply: a mock `ConsensusTransport` returning different terms per peer, asserting `getState() !== 'leader'` after the loop. Not implemented tonight (surfaced by the SCAN role, not the DEEP surface; a genuine consensus-safety bug deserves its own focused night rather than a rushed same-night fix) — recommend prioritizing this for the next `swarm` or `hive-mind`-adjacent DEEP night, since it is a correctness bug, not a research question.
